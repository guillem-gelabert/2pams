# Summary

Prepared a two-service Railway topology with a shell at `2pa.ms` and content on a separate Railway origin. The shell only redirects proxied URLs. The content role hides the landing page and applies its own response policy.

Added an opt-in Playwright fallback for recognized DataDome challenges on configured upstream hosts. It runs one isolated browser visit at a time, checks each browser request against an explicit host list and the existing SSRF guard, and serves a script-free snapshot only when the challenge clears and visible content is present. Cookies stay inside the short-lived browser context.

Added `Dockerfile.browser` and `railway.browser.toml` for the content service. No Railway or Cloudflare resources or production variables were changed. The existing Railway project currently has only one service with a 500 MB memory limit; deploying the fallback needs a second service and a higher memory allocation.

Verification: TypeScript build, Prettier check, ESLint (only existing startup `console` warnings), all five Playwright tests, manual shell redirect/CSP and content-root checks, Docker image build, and full Chromium launch as non-root. Automated tests used a controlled local challenge and `example.com`; no El País requests were made.

Limit: Playwright may still be rejected or require a human CAPTCHA. This prototype has not been validated against the target article. Railway deployment and manual article verification remain separate steps.
